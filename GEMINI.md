# GEMINI.md — контекст проекта «ЧПУ Система»

Этот файл Gemini CLI читает при каждом запуске в репозитории. Здесь — то, что
нужно знать, прежде чем трогать код: что это за система, жёсткие правила, где
что лежит и как проверять работу. Подробности — в документах по ссылкам; этот
файл их не заменяет, а говорит, что и когда читать.

> Состояние проекта (что выложено, что ждёт, что дальше) меняется каждую неделю
> и живёт в [CONTINUE_HERE.md](CONTINUE_HERE.md), раздел «Статус». Числа
> (тесты, записи в базе, миграции на проде) проверяй командой, а не по тексту:
> документация в этом проекте уже дважды подводила в обе стороны.

## 1. Что это

Складской учёт, продажи (касса), клиенты и финансы для мастерской ЧПУ- и
лазерной резки в Бишкеке (акрил, форекс, оргстекло, алюкобонд, баннер,
самоклейка). Владелец всю жизнь вёл склад и деньги в Excel; главное требование —
**минимум ручного ввода при полном паритете с его таблицей**. Валюта — сом,
цены округляются вверх до целого сома.

- Бэкенд: **Python 3.13 + Django 6.0 + DRF + SimpleJWT**, локально SQLite, на
  проде PostgreSQL 17 в Docker.
- Фронтенд: **React 18 + Vite 5**, `react-router-dom` 6, `i18next` (RU/KY/EN),
  без UI-библиотек и без TypeScript. Каталог `frontend/`.
- Прод: https://chpucenter.com — Cloudflare → nginx на хосте → gunicorn в
  Docker. Подробно — [DEPLOY.md](DEPLOY.md).
- Язык проекта — **русский**: документы, комментарии, коммиты, общение с
  пользователем.

## 3. Жёсткие правила (нарушать нельзя)

### Данные и миграции

- **На проде боевые данные** (с 2026-08-18). Схема меняется **только новой
  миграцией поверх**: колонка и перенос данных — разными миграциями, обратимо.
- **Никогда не переименовывать и не переписывать миграцию, которая могла уйти на
  сервер.** 19.09 переименование `finance/0008` уронило прод на 502:
  `migrate` в `deploy/entrypoint.sh` упал на повторном добавлении колонки, и web
  не поднялся. Нужна другая структура — новая миграция сверху.
- Никаких `docker compose down -v`, пересборок `0001_initial`, удаления
  `db.sqlite3` без вопроса.
- Перед правкой, которая меняет прошлые цифры (прибыль, долг, склад), —
  **посчитать затронутые записи** (локально `manage.py shell`, на проде — команду
  для пользователя) и спросить владельца.
- Перед пересозданием любой базы — посчитать записи. Не нули — остановиться и
  спросить, что это за данные. «Тестовые, сносите» может сказать только
  пользователь.
- После правки моделей: `python manage.py makemigrations --check --dry-run`
  должен говорить `No changes detected` (CI проверяет то же).

### Решения владельца

- Как считать деньги, что входит в резку, что показывать — **решает владелец**.
  Спрашивай, а не додумывай. Решения из `docs/DECISIONS.md` окончательные: не
  «чинить» их обратно, даже если выглядят как баг (список таких мест — раздел 6).
- Новое поле ввода — только если значение нельзя вывести из того, что система
  уже знает. Автоматическое значение всегда можно перебить вручную, и ручное
  побеждает расчёт.
- Названия, формулировки и привычные термины владельца («синий бишкек», «длина
  кривой», «одна сторона») не переименовывать.

### Git

- **Не коммитить и не пушить без явной просьбы.**
- Коммиты — **по-русски**, осмысленный заголовок + при необходимости тело «что и
  почему». **Без упоминаний ИИ-ассистентов и без служебных trailer'ов**
  (`Co-Authored-By`, `Generated with …`) — это жёсткое правило пользователя.
- На сервере не коммитят: там только `git pull`.
- Пуш по SSH с этой машины не работает; если пользователь попросит запушить —
  через HTTPS и `gh` (`git -c credential.helper='!gh auth git-credential' push
  https://github.com/lev1tha/typography_wherehouse.git <ветка>`).

### Секреты и доступы

- Паролей в репозитории нет и не должно быть: ни в коде, ни в документах, ни в
  коммитах. Пароли старых учёток когда-то лежали в документах и истории git —
  они считаются скомпрометированными.
- `.env`, `.env.prod`, `db.sqlite3`, дампы базы — не коммитить.
- **Доступа к серверу у ассистента нет.** Выкладку делает пользователь. Команды
  для сервера давай готовыми блоками с ожидаемым выводом. На сервере оболочка
  **fish**: многострочные heredoc (`manage.py shell <<'EOF'`) — только из `bash`.

## 4. Запуск

```bash
# бэкенд, порт 8710 (голый runserver сам встаёт на 8710)
source .venv/bin/activate
python manage.py migrate
python manage.py createcachetable    # иначе вход отдаёт 500: кеш в таблице БД
python manage.py runserver

# фронтенд, порт 5710, проксирует /api и /media на 8710
cd frontend && npm install && npm run dev
```

- **Порты свои — 8710/5710**, не 8000/5173: на машине одновременно работают
  несколько проектов. Если порт занят — `BACKEND_PORT=…` (двигает и бэкенд, и
  прокси Vite) и `FRONTEND_PORT=…`. Пустые таблицы во фронте почти всегда
  значат, что бэкенд не поднят: `lsof -nP -iTCP:8710 -sTCP:LISTEN`. Если логин
  отдаёт 404 на `/api/token/` — на порту чужой проект.
- Локальная база — с данными ручного прогона, не чистая. Учётки: `admin`,
  складовщики `Лазер` и `Чпу`, бухгалтер `Бухгалтер`; пароли — у пользователя.
- `seed` на рабочей базе не запускать (заведёт лишние учётки `storekeeper`/
  `accountant` и заготовку каталога). `seed_demo` — только когда явно нужны
  демо-данные.
- Экраны «Финансы», «Касса», «Ведомость» и «Обзор» закрыты вторым паролем
  `FINANCE_PASSWORD` из `.env` (`FinanceGate` во фронте, проверка на бэкенде).
- Django-админка — **`/django-admin/`**, не `/admin/`: `/admin/*` — экраны React.
  Префикс прописан в `config/urls.py`, `deploy/nginx/chpucenter.com` и
  healthcheck в `docker-compose.prod.yml` — менять только вместе.

## 5. Тесты и проверки

```bash
python manage.py test --parallel 4                 # ~2400 тестов, все зелёные, ~35 с
python manage.py test sales.tests_edge_01          # один модуль
python manage.py test --shuffle 1                  # случайный порядок
python manage.py makemigrations --check --dry-run  # модели и миграции совпадают
cd frontend && npm run build && npm run lint:css-vars
```

- Тесты лежат рядом с кодом: `<app>/tests.py` и `<app>/tests_*.py` (их сотни
  файлов — ищи по имени темы: `tests_leftovers.py`, `tests_supplier_wave1.py`…).
- На SQLite 7 тестов гонок пропускаются; на PostgreSQL идут все
  (`DATABASE_URL=postgres://…`). CI гоняет PostgreSQL 17.
- Тесты не зависят от текущей даты: даты считают от середины месяца или
  фиксируют часы (`freeze_now` в `warehouse/tests_stock_on_date.py`).
- `finance/tests_golden.py` — квартал операций с итогами, посчитанными руками.
  Если он покраснел, неправ код, а не тест.
- Бэкенд-тесты не ловят расхождений между экранами. Изменения интерфейса
  проверяй живьём в браузере; печать — только через PDF (`page.pdf()` в
  Playwright), предпросмотр печати обманывает.
- Разграничение ролей на работающем сервере — `python manage.py check_roles`.

## 6. Бизнес-правила, которые выглядят как баги, но ими не являются

**Деньги** (полностью — `HANDOVER.md` раздел 7 и `docs/DECISIONS.md`):

- Два отчёта — два вопроса. **ОПиУ** (метод начисления) — «сколько заработали»:
  заказ в долг уже выручка. **ОДДС** (прямой метод по кассе) — «сколько денег».
  Разницу объясняет вкладка «Сверка», «Не объяснено» обязано быть 0.
- Прибыль по шагам: выручка − себестоимость − брак и недостача = валовая;
  − расходы цеха ± недостача/излишек кассы = до амортизации и налога;
  − амортизация − проценты − налог (4 % от выручки с 10.2026, по истории ставок)
  = чистая прибыль. Каждый месяц ОПиУ равен «Сводке» — на это есть тест.
- **Себестоимость проданного — не расход, а оборот**; закуп тоже не расход.
  Инвестиции — отдельный блок, в прибыль не входят. Станок и ремонт от 20 000
  амортизируются 60 месяцев.
- Расход относится к месяцу, **за который** он (поле «За какой месяц»), а не к
  дню оплаты. **Возврат — днём возврата**, не днём заказа.
- Дата оплаты отчёты не двигает: выручка — по дате заказа (`Receipt.created_at`,
  задаётся вручную, хранится полднем местного времени).
- **Приход без указанной оплаты — долг поставщику** (D-195).
- Закрытый месяц (замок периода) не правится задним числом — ни деньги, ни
  склад, ни правка партии.

**Касса и продажи:**

- Пустая сумма оплаты = ничего не приняли, весь заказ в долг. Переплата — сдача,
  она зачитывается в следующий заказ клиента (в кассовую книгу зачёт не пишется).
- Отмена оплаты — встречная запись, прошлое не переписывается.
- Резка — **две строки**: материал (площадь × цена/кв.м) + работа (погонный метр
  × ставка станка). **Пог.м и кв.м не смешивать.** «Одна сторона» считает одну
  сторону куска — это решение владельца, не баг. Резка без длины — 400, а
  `cut_rate=0` — законный подарок.
- Рулон продаётся погонными метрами (или по кв.м изделия, если задана вторая
  цена), лист — площадью или целиком. Возврат идёт в те партии, откуда взят.
- Себестоимость — FIFO по партиям, фиксируется в момент продажи.
- Все денежные строки округляются **вверх до целого сома**.
- Правила прайса (минимум, округление заказа, срочность, скидка, договорные
  цены, лимит долга) **по умолчанию выключены** — пока владелец их не задал,
  цена считается как раньше.
- Отдельных счетов MBank/DemirBank в кассе нет — исключено владельцем.

**Роли:** складовщик **не видит закупочных цен** — в API вместо них `null`
(не «0»). Бухгалтер — проверяющий: всё только на просмотр. Разграничение держит
сервер, а не меню.

## 8. Правила кода

**Бэкенд:**

- Пиши как окружающий код: русские комментарии там, где объясняют «почему»;
  бизнес-правило со ссылкой на решение (`D-123`) — так принято.
- Денежная логика — в сервисах (`sale_service.py`, `finance/reports/`,
  `warehouse/*.py`), не во вьюхах и не в сериализаторах.
- Деньги — `Decimal`, никогда `float`.
- Новое бизнес-правило — сразу тест. Новое решение владельца — строка в
  `docs/DECISIONS.md` (следующий свободный номер D-…).
- Неизвестные поля в денежных запросах — 400, а не молча (D-83).
- Денежные операции блокируют строку чека (`select_for_update` внутри
  транзакции) — не обходить.

**Фронтенд:**

- **Любая новая строка интерфейса — во все три словаря** `ru.json`, `ky.json`,
  `en.json`. Кыргызские тексты пишет не носитель — помечай в отчёте, что
  нужна проверка.
- Деньги, числа, даты — только через `utils/format.js`.
- Формы — через `Field` (ошибка под полем), окна — через `Modal`/`useDialog`,
  щелчок по затемнению окно не закрывает. Списки с сервера — постранично
  (`Pager`), выбор клиента — `ClientPicker`.
- **У каждого `await api.*` — `catch` с понятной ошибкой.** «Кнопка не
  нажимается» у владельца почти всегда значит молчаливый 400 от сервера.
  Пустое числовое поле уходит строкой `""` — проверяй сценарий «стёр цену,
  чтобы вписать заново».
- Цвет текста — только текстовые токены (`--*-ink`), фокус виден всегда,
  без горизонтального скролла на 375/768/1280 ни в одном языке. Проверка
  переменных — `npm run lint:css-vars`.

## 9. Как работать с пользователем

- Отвечай **по-русски, коротко и по-человечески**, без стен текста. Тепло, без
  оборонительности. Если пользователь путается — это вина системы, а не его.
- Показывай результат живьём (поднятое приложение, запрос к API, прогон
  тестов), а не описанием «должно работать».
- Бизнес-вопросы — спрашивай. Технические мелочи — решай сам и скажи, что выбрал.
- Сообщай честно: тесты упали — покажи вывод; что-то не проверено — так и
  скажи.

## 10. Как обновлять документацию

- После заметной правки обнови `CONTINUE_HERE.md` (статус, ждущие миграции,
  шаги выкладки), архитектурное — в `HANDOVER.md`, решение — в
  `docs/DECISIONS.md`.
- Не пиши в документы чисел, которые не проверил командой (число тестов —
  прогоном, содержимое базы — запросом).
- Пароли, токены и адреса с секретами в документы не попадают.

## 11. Команды аудита

`/audit` (файл `.gemini/commands/audit.toml`) — аудит глазами владельца цеха:
ищет, где система врёт про деньги и остатки, ничего не правит.
