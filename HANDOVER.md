Нужны 2 терминала, из корня репозитория.

**Бэкенд (порт 8000):**
```bash
python3 -m venv .venv && source .venv/bin/activate   # первый раз
pip install -r requirements.txt                       # первый раз
cp .env.example .env                                  # первый раз
python manage.py migrate
python manage.py seed        # 2 аккаунта + каталог + услуги (идемпотентно)
python manage.py runserver 127.0.0.1:8000
```

**Фронтенд (порт 5173):**
```bash
cd frontend
npm install                  # первый раз
npm run dev                  # http://localhost:5173 (проксирует /api на :8000)
```

можно поднимать через Claude-Preview `preview_start`.

> из-за чего выглядело как случайный глюк.
>
> На деве не воспроизводится вовсе: Vite проксирует на Django только `/api` и
> `/media`, поэтому `/admin/finance` там всегда отдаёт фронтенд. Ловится только
> на проде. Сторожат тесты в `accounts/tests.py`.
>
> Префикс прописан в трёх местах, менять их вместе: `config/urls.py`,
> `deploy/nginx/chpucenter.com` (`location ~ ^/(api|django-admin)/`) и
> healthcheck в `docker-compose.prod.yml`.

## 3. Склад: рулоны, листы, единицы

Материалы приходят в разных формах, всё считается в **кв.м** (для площадных):
- **Лист** (акрил 1.22×2.44 и т.п.): площадь = ширина × высота × кол-во листов.
- **Рулон** (форекс, самоклейка): ширина фикс, длина РАЗНАЯ → площадь = ширина × длина.
- **По количеству** (клей, краска, крепёж): кг/л/шт, без площади.

**Номенклатура разобрана на поля.** Заказчик писал свойства строкой («Орг
стекло 2мм 180*121см», «ЖЕЛТЫЙ лимон 2,5ММ 237»), поэтому ни отфильтровать по
толщине, ни вывести площадь листа из размера было нельзя, а отчёт по резке
угадывал тип подстрокой и ошибался: «синий бишкек», «день ночь» и «салатовый»
это акрил, но падали в «Прочее». Теперь у `Material` есть `type` (FK на
справочник `MaterialType`), `thickness_mm`, `color`, `article`, `sheet_width`,
`sheet_height`; свободного текста `category` больше нет.

- **Форма материала задана на нём самом** — `Material.intake_form`
  (`SHEET` / `ROLL`, миграция `warehouse/0004`). В карточке материала вместо
  галочки «листовой/рулонный» три кнопки: **Штучный · Лист · Рулон**. Галочка
  отвечала на «считаем в кв.м?», но не на «чем он приходит», и форму складовщик
  выбирал заново в каждом поступлении. Теперь она подставляется в приход (и
  **«Лист» стоит первым**, листами приходит почти всё), а подписи цен говорят
  «за лист» или «за рулон» — по этому же полю. Старым материалам форма проставлена
  по их последней партии (data-миграция в том же файле).
- **Приход показывает старую и новую цену**: рядом с себестоимостью партии
  стоит текущая закупочная (сом/кв.м и сом/лист), а в итоге — новая с пометкой
  «было X». Заказчик покупает листами и цену помнит за лист.
- **Площадь листа считается из размера** (`Material.save`), вручную вводится
  только у материалов без размеров.
- **Название собирается из полей** (`suggested_name`) и остаётся редактируемым:
  у заказчика свои привычные подписи вроде «синий бишкек», отнимать их нельзя.
- **Стоимость склада считается по ПАРТИЯМ** (`Material.stock_value`): у каждой
  партии своя себестоимость, берём остатки партий, самые старые первыми (ими и
  спишется), остаток сверх партий (его создаёт инвентаризация) — по последней
  закупочной цене. Было `quantity × purchase_price`, а `purchase_price` — цена
  ПОСЛЕДНЕГО прихода: подорожал акрил вдвое, и вдвое дорожал весь давно лежащий
  остаток. Цифру показывает «Обзор» (`unrealised_asset`); тесты —
  `warehouse/tests_stock_value.py`.
- **Точность площади — четыре знака.** При двух 1.22 × 2.44 = 2.9768
  округлялось до 2.98, и 50 принятых листов показывались как 49.95 ровно в той
  колонке, которую он сверяет со своим Excel. `quantity`, `piece_area`,
  `initial_area`, `remaining_area`, `quantity_changed` — `decimal_places=4`.
- Типы заводит админ (`/api/warehouse/material-types/`), встроенные создаёт
  миграция `warehouse/0002`. Разбивка резки в финотчёте строится по типам
  динамически: показываются только те, по которым в периоде резали.

**Каталог заводится пачкой** — «Склад → Материалы → Ввести пачкой»
(`components/CatalogGrid.jsx` → `POST /api/warehouse/materials/bulk/`). Строка =
материал, Tab между полями, Enter вниз, вставка куска таблицы из буфера
(Ctrl+V) сразу в несколько строк и столбцов; название справочника из буфера
(«Форекс») подставляется в выпадающий список, ненайденное показывается как
«Форекс — ?», а не молча пустой ячейкой.

> **Вёрстка сетки — три неочевидных решения, не «чинить» обратно** (`.grid-*`
> в `index.css`). Одиннадцать колонок в обычной модалке (520px) показывали три,
> поэтому у `Modal` есть проп `wide` (`min(1440px, 96vw)`), подписи внутри
> групп короткие, а шапка двухъярусная: «Материал · Лист, м · Цены, сом» с той
> же заливкой, что в складском листе. На 1280px всё влезает без прокрутки.
> - `border-collapse: separate` — при `collapse` Chrome не приклеивает ячейки
>   по горизонтали, и номер строки с названием уезжали за край: правые колонки
>   заполнялись вслепую.
> - `overflow: visible; border: 0` поверх `.table` — `overflow` базового класса
>   создаёт свой контекст прокрутки и убивает `sticky` вовсе. Рамку и скругление
>   рисует обёртка `.grid-wrap`.
> - `.grid-table { display: table }` внутри мобильного брейкпоинта — там
>   `.table { display: none }` (таблицы заменяются карточками), а у сетки
>   карточного двойника нет, и на телефоне окно было пустым.

> **Импорта из xlsx нет и не будет: файла у заказчика не существует** — не «пока
> не прислал». Разбирать чужую таблицу вслепую не под что, а сетка закрывает ту
> же задачу и не зависит от файла. Если файл когда-нибудь появится, разбор
> пристраивается к этому же экрану — сетка уже принимает таблицу целиком.
>
> В сетке НЕТ намеренно: закупочной цены (приходит с партией), галки «листовой»
> (выводится из наличия размера листа), площади листа (считается из размера) и
> единицы измерения (кв.м у листового, шт у остального). Колонка «цена за
> лист/шт» пишется в `piece_price` у листового материала и в `price_per_unit` у
> штучного — смысл один, а поле в модели разное.
>
> Сохранение — **всё или ничего**: одна опечатка в 47-й строке не должна
> оставить в базе 46 материалов, которых потом не найти. Ошибки возвращаются с
> номерами строк, сетка их подсвечивает. Занятость названия и дубли внутри самой
> пачки проверяются приведением регистра **в Python**, а не через `name__iexact`:
> SQLite складывает регистр только для латиницы, и «форекс» разошёлся бы с
> «Форекс» на деве, но совпал на проде (PostgreSQL).

Модель `Material`: `unit` (SQM/METER/PIECE/KG/LITER), `is_roll_material` (в UI
подписан как «Листовой/рулонный (по кв.м)» — списывается из партий по площади).
Модель `Roll` (партия/лот): `form` (ROLL/SHEET), размеры, `initial_area`/
`remaining_area` (кв.м), `purchase_cost` → `cost_per_sqm`, `received_at`.
Розничная цена материала (`price_per_sqm`/`price_per_unit`) задаётся отдельно,
вручную, на Складе.

> `markup_percent` у партии **удалён**: наценку спрашивали при каждой приёмке,
> но производную от неё `Roll.price_per_sqm` не читал никто — цена продажи
> берётся из `Material.sqm_price`. Ручной ввод впустую, да ещё и вводящий в
> заблуждение: человек думал, что задаёт цену продажи.

**Дата поступления редактируемая.** `InventoryLog.happened_at` (бывший
`created_at`) и `Roll.received_at` были `auto_now_add`, то есть внести поставку
задним числом было нельзя вообще — а заказчик работает именно так: в его Excel
даты идут вразнобой (01, 05, 06, 10, 14, 19 июля), он вносит, когда доходят
руки. Июльская поставка, введённая в августе, уезжала в август, и складской
лист расходился с его таблицей. Дата принимается в приёмке
(`received_on`/`happened_on`); по ней же строится FIFO, поэтому партия задним
числом встаёт в очередь на списание по своей настоящей дате.

**Продажа листом целиком** — `piece_price` (цена за лист) + `piece_area`
(площадь листа, для списания). Есть **опт**: `wholesale_price` + `wholesale_min_qty`
(минимум листов) — при продаже от этого количества цена за лист сама
переключается на оптовую (`Material.piece_price_for_qty`), с бейджем «Опт» в
кассе. Ручной override цены на кассе — всегда в приоритете.

`warehouse/rolls.py`:
- `receive_lot(...)` — создаёт партию, считает площадь, обновляет остаток
  материала и его себестоимость (`purchase_price` = себестоимость последней
  партии; розничную цену admin выставляет отдельно на Складе).
- `consume_area(...)` — списывает кв.м **FIFO** по партиям (старые первыми),
  бросает `InsufficientStock`, если не хватает.
- `restore_area(...)` — возврат площади (рефанд), доливает партии в том же
  порядке, в каком списывались, не превышая исходную площадь партии.

**Журнал движений (`InventoryLog`) пишет ВСЁ, включая продажи.** Типы:
`SUPPLY` · `SALE` · `RETURN` · `WRITE_OFF` · `ADJUSTMENT`. У записи есть ссылка
на чек (`receipt`), поэтому строка ленты отвечает не только «сколько ушло», но и
«по какому заказу».

> Раньше продажи в журнал **не попадали вовсе**: `sale_service._deduct` вызывал
> списание без `log_type`, а запись лога стояла именно под ним (в `rolls.py` —
> под непустым `reason`). Возврат ШТУЧНОГО материала при этом писался, и в
> журнале висел приход без парного расхода. Теперь запись делается по
> `log_type` в обеих функциях; `log_type=None` — «двигай остаток, лог не пиши»
> (так ходит внутренняя механика, где движение уже записано другим вызовом).
> Заодно чинился 500 на `/inventory-logs/`: сортировка ссылалась на `created_at`,
> которого у модели нет с тех пор, как приходы научились датироваться задним
> числом. Ни один экран журнал не показывал, поэтому не замечали ни того, ни
> другого — тесты на обе вещи лежат в `warehouse/tests.py`.

Складской лист («Остатки по месяцам») продажи по-прежнему считает по строкам
чеков, а не по журналу, — журнал ему не источник, двойного счёта нет.

UI: единый раздел **«Склад»** (`pages/admin/Stock.jsx`) с тремя вкладками:
«Материалы» (каталог, `Catalog.jsx`), «Движение» (`Supply.jsx` — журнал,
инвентаризация, списание) и **«Остатки по месяцам»**
(`MaterialStock.jsx`) — складской лист заказчика: поступление · проданные ·
производство · выручка (материал / резка / всего), плюс колонки приходов по
датам. **Колонок «остаток в начале» и «остаток в конце» больше нет** (просьба
заказчика, 2026-08-14) — вместе с ними ушёл и ручной ввод остатка на начало в
клетке. API их всё ещё считает и отдаёт, вернуть колонки — правка одного
компонента. Из «Финансов» на эту вкладку ведёт ссылка. Приём партии рулона/листа доступен и
прямо с карточки материала (кнопка «Поступление», `ReceiveStockModal`).
Списание — причины порча/брак/утеря/срок (тип лога `WRITE_OFF`, учитывается в
потерях дашборда). **Рулон списывают по конкретному рулону и в метрах**
(`POST /rolls/<id>/write-off/` → `write_off_roll`: его шириной, по его цене,
в журнале «Рулон №N: 2 м»); общее `/materials/write-off/` для `sells_by_metre`
отвечает 400 — оно шло FIFO со старейшего рулона, и «порвали 2 м рулона №8»
обнуляло целый №7 (2026-08-18, аудит п. 7; `warehouse/tests_roll_write_off.py`).
Вкладка «Списание» при выборе рулонного материала спрашивает рулон и метры.

**Лента «Движение»** (`components/StockJournal.jsx`) — первая вкладка внутри
«Движения»: все операции подряд, свежие сверху, по 25 на страницу. Фильтры:
тип операции · материал · месяц. Месяц по умолчанию НЕ выбран (`«Все месяцы»`):
поставки вносят задним числом, и лента, обрезанная текущим месяцем, прятала бы
приход ровно в момент ввода. Фильтр по типу стоит первым потому, что продаж в
ленте больше всего — по записи на каждую товарную строку чека.

**Приходная накладная (2026-08-14).** Поставка вводится ОДНИМ документом:
`Supply` + строки `SupplyLine`, экран — Склад → «Приходы» (`pages/admin/Supplies.jsx`).
Раньше приход вводился по одной позиции с кнопки на строке материала: поставка
на восемь позиций — восемь операций, и сверить итог с бумагой было нечем.

- **Проводится сразу при создании** (`warehouse/supplies.py::post_supply`) —
  строки уходят на склад ТЕМИ ЖЕ примитивами, что и одиночный приход:
  `receive_lot` для площадных (создаёт партию со своей себестоимостью → FIFO и
  стоимость склада), `apply_stock_change` для штучных. Своей механики склада у
  документа нет намеренно: любой второй путь записи рано или поздно разойдётся
  с журналом и закупом.
- **Сверка с бумагой** — ради неё всё и затевалось: `stated_total` (сумма как в
  накладной поставщика) против `total_cost` (сумма строк), разница — в колонке
  «Расхождение».
- **Долг поставщику** = `total_cost − paid_amount` по каждой накладной, в
  справочнике поставщиков — суммой по всем его накладным.
- **Закуп в финотчёте берёт ТОЧНУЮ сумму строки**, а не цену за единицу
  (`purchases_from_stock`): 48 000 / 29.768 кв.м округляется до 1612.47, обратно
  даёт 48 000,01 — и закуп переставал сходиться с накладной ровно там, где
  заказчик их и сверяет. Одиночные приходы (без документа) по-прежнему считаются
  через цену за единицу: суммы у них нет.
- **Дата накладной — полдень местного времени** (как у даты заказа): полночь в
  Бишкеке это вчерашний вечер по UTC.
- **Строка накладной без суммы** не выпадает молча: сетка держит кнопку
  закрытой и называет строку, сервер требует `cost ≥ 0` (аудит п. 9). Ширина
  рулона в накладной подставляется из карточки (`post_supply` и сетка),
  отличная от карточки — подсвечена (аудит п. 10).
- **Отмена** (`unpost_supply`, только админ) снимает всё принятое с остатков и
  удаляет партии — но ТОЛЬКО пока из них не резали: иначе поехала бы
  себестоимость закрытых заказов. Состав проведённого документа не правится по
  той же причине; номер, дата, сумма по бумаге и оплата правятся спокойно.
  Перенос даты накладной (`PATCH received_on`) двигает партии и движения
  склада за собой (`move_supply_date`) и держится замком периода с обеих
  сторон (аудит п. 13).
  Движения склада по отменённой накладной УДАЛЯЮТСЯ (как у удалённого чека),
  след с составом — в журнале действий (`supply_summary`). Раньше логи
  оставались, отвязанные от документа, и считались одиночными приходами —
  закуп месяца держал сумму отменённой накладной навсегда (2026-08-18, аудит
  п. 6; `warehouse/tests_supply_cancel_purchase.py`).
- **Справочник поставщиков** (`Supplier`): заводит его тот, кто принимает товар
  (складовщик тоже) — новая фирма всплывает в момент приёмки. Удаляет админ;
  поставщик с накладными скрывается, а не удаляется.
- Записи журнала ссылаются на накладную (`InventoryLog.supply`), так что из
  ленты движений видно, по какой бумаге пришёл материал.
- **Накладная печатается** (`components/PrintSupply.jsx`, кнопка в карточке
  документа). Бумага поставщика остаётся у поставщика — цеху нужен свой лист,
  который подписывает принимающий. На нём же напечатана сверка: сумма по бумаге,
  принятая сумма и расхождение; этот лист и показывают поставщику при споре о
  недостаче. Подписи — «Сдал» и «Принял» (кто оприходовал).

Миграция `warehouse/0005`. Тесты — `warehouse/tests_supplies.py` (20 штук:
проведение, сверка, права, отмена, попадание в финотчёт).

**Удаление материала (админ).** `DELETE /materials/<id>/`. Граница проходит по
**продажам**, а не по любой истории:

- **продаж не было** — материал удаляется НАСОВСЕМ вместе с партиями и
  складским журналом. Значит уходит и из закупа (он считается по приходам), и
  из стоимости склада, и из django-админки;
- **продажи были** — материал только **скрывается** (`is_archived=True`):
  строки старых чеков на него ссылаются, и удаление сдвинуло бы суммы закрытых
  заказов. Скрытый материал не показывается ни в каталоге, ни в кассе, **не
  считается в стоимости склада и в «материалах на исходе»**, а в отчёте по
  материалам остаётся только там, где в периоде реально были движения (иначе
  выручка того месяца не сошлась бы). Посмотреть скрытые — `?archived=1`,
  вернуть — `POST /materials/<id>/restore/`.

> Раньше граница шла по любой истории, и материал прятался уже из-за одного
> прихода — а это самый частый случай: завели материал, приняли поставку,
> увидели дубль. Заказчик сообщил это как «нажимаешь удалить, из вида пропадает,
> а в django-админке и в финансах остаётся» (2026-08-14). Оба пути проверены в
> `warehouse/tests_delete.py`. Ответ на DELETE всегда 200 с `detail` — интерфейс
> показывает его тостом, чтобы «удалён» и «скрыт» не выглядели одинаково.

Эндпоинты: `/api/warehouse/materials/` (+ actions `bulk`, `receive-roll`,
`supply`, `adjust`, `write-off`, `update-price`, `restore`),
`/api/warehouse/rolls/` (+ actions `stocktake`, `write-off`),
`/api/warehouse/inventory-logs/`.

Списки поддерживают `?page_size=` (потолок 500, `config/pagination.py`).
Выпадающие списки материалов грузятся целиком: страница в 25 строк молча
обрезала каталог, и материала №26 в выборе просто не было.

## 4. Услуги: резка, установка

`PrintingService.kind`:
- **CUTTING (резка)** — по кв.м. Это единственный активный вид услуги в кассе.
  Любой рез (кроме «целого листа без отреза») даёт **две строки чека**: работа
  мастера (погонный метр реза × `cut_rate_per_pm` материала — ставка резки
  задаётся на самом материале, не на услуге) + материал (площадь × цена/кв.м).
  **Длина реза («длина кривой», пог.м) приходит из кассы:** у фигурного реза её
  вводит мастер, у обычного касса берёт одну сторону куска (поле «Длина»).
  На бэкенде правило прежнее — не пришла, работа = 0. Площадь вместо длины не
  подставляется: кв.м считались как пог.м (для листа 1.22×2.44 — 2.98 вместо
  7.32), и работа стоила примерно втрое дешевле. `PrintingService.rate_flat` — легаси-поле
  (участвует только в старом расчёте `uses_area` для не-CUTTING кейсов).
- **INSTALL_EXTERIOR / INSTALL_INTERIOR (установка)** — модели и код на месте
  (per-piece / area+material), но **деактивированы** (`is_active=False`) по
  решению заказчика — `seed.py` выключает их явно. Не удалены, чтобы не
  порвать `PROTECT`-ссылки из истории старых чеков. Если понадобятся снова —
  включить `is_active=True`.
- **OTHER / INSTALLATION (legacy)** — фикс. цена за заказ, не используется.

`ServiceRecipe` (техкарта доп. материалов, напр. крепёж/клей): `material`,
`consumption_per_unit`, `consumption_mode` (PER_SQM/FIXED). Поле `applies_to`
сейчас имеет только значение `ALL` — деление на «плоские/объёмные буквы»
убрано вместе с install-услугами. Резка сама по себе рецепты не использует
(материал реза — отдельная строка чека, не техкарта); `seed.py` явно чистит
legacy-рецепты резки. Если техкарту резке всё же заведут (через админку —
в UI они только читаются), норма «на кв.м» считается от ПЛОЩАДИ куска
(`width × length` строки резки), а не от её `quantity` — это погонные метры
(`sales/sale_service.py::recipe_consumption`, аудит 18.08 п. 16).

`PricingSettings.master_commission_percent` — % ЗП мастера от стоимости
работы резки. Справочное поле админа (редактируется на странице «Цены и
услуги»); финотчёт показывает РАСЧЁТНУЮ долю (`cutting.master_share`, и по
сотрудникам) — в прибыль/P&L она **не** подставляется, зарплаты вносятся
записями (аудит 18.08 п. 17).

Расчёт и списание — `sales/sale_service.py::_build_item` и
`_deduct_stock_for_item`.

## 5. Продажи (POS), долг, возвраты, дозаказ

**Оформление продажи** (`/app/checkout` у складовщика, `/admin` у админа —
касса теперь главный экран обеих ролей) — POS-стиль: слева сетка
товаров/услуг (карточка материала краснеет и блокирует продажу при нулевом
остатке), справа живой чек + блок клиента (живой поиск по имени, «Кто привёл»
для нового клиента) + способ оплаты + «Оформить».

**Четыре способа продать материал по кв.м** (окно материала в кассе,
2026-08-14 — формулировки заказчика):

| Режим | Что вводят | Материал | Работа реза |
|---|---|---|---|
| **Одна сторона** (по умолчанию) | ширина × длина | площадь × цена/кв.м | **пог.м = «Длина»**, одна сторона куска |
| **Длина кривой** | ширина × длина + длина кривой | площадь × цена/кв.м | пог.м × ставка, длину вводит мастер |
| **Квадратный метр** | ширина × длина | площадь × цена/кв.м | нет |
| **Штучный** | количество + цена за лист/рулон | цена за штуку × кол-во | по желанию, галкой |

Раньше вкладок было две («Отрезать кусок» и «Весь лист»), и в первую попадали
три разных случая — фигурный рез, обычный рез и продажа площади без реза;
отличались они только тем, что мастер вписал (или не вписал) в поле погонных
метров. **«Длина реза» переименована в «длину кривой»** везде.

> **Обычный рез считает ОДНУ сторону** — ту, что в поле «Длина». Это не откат
> старого бага (там в пог.м подставлялась ПЛОЩАДЬ, и работа выходила втрое
> дешевле): площадь и одна сторона — разные вещи, кв.м с пог.м по-прежнему не
> смешиваются. Бэкенд не изменился: он как и раньше берёт `running_meters` из
> запроса и без них не начисляет работу — считает сторону касса.

> **Режим уходит на сервер ЯВНО (`mode` в `SaleItemInputSerializer`,
> 2026-08-18, аудит п. 2).** У листа/рулона он обязателен (без него сервер
> раньше молча считал «кв.м»: дозаказ «1 лист» → 1 кв.м по цене за квадрат),
> рулон принимает только `METER` (площадь продавала его за 0 — цены за кв.м у
> рулона нет), `METER` — только у рулона; резка с материалом-рулоном и
> размерами куска отклоняется, работа реза по рулону — строкой без размеров.
> Штучный материал режима не требует. См. `sales/tests_sale_mode_required.py`.
> **Неявный ноль — отказ, явный — подарок (аудит п. 8):** без override и без
> ставки/цены в каталоге (у станков `rate_per_pm = 0` — «берётся у материала»,
> у материала нет ставки резки или цены за кв.м / лист / пог.м / единицу)
> строка отклоняется с указанием, чего не хватает; `cut_rate=0` /
> `material_price=0` явно — подарок админа. Касса шлёт override только если
> админ правил поле (`*Edited`), строка «Работа» видна и при нулевой ставке.
> См. `sales/tests_implicit_zero_price.py`.

**Цена за лист/рулон правится прямо в кассе** (админ, режим «Штучный»), как и
цена за кв.м у куска. Пока её не трогали, работает оптовая цена от нужного
количества; вписанная руками цена опт отменяет и уходит на сервер как
`material_price`. То же слово «лист» или «рулон» подставляется из
`Material.intake_form` — «цена за лист» у плёнки отвечала не на тот вопрос.

**Закрытие периода (2026-08-14).** `finance.PeriodLock` — одна дата
(`closed_through`), по которую всё «на замке»; экран — Финансы → «Закрытие
периода». Отчёт за июль, который владелец уже посмотрел и принял, мог назавтра
показать другую цифру: даты заказов, трат и приходов правятся задним числом, а
журнал действий это записывает, но не останавливает.

- Проверка ОДНА на всю систему: `finance/periods.py::ensure_open(day, what)`.
  Ошибка — `ValidationError` DRF, поэтому любой эндпоинт отвечает 400 с текстом
  «…нельзя: период закрыт по 31.07.2026», и ловить своё исключение в каждой
  вьюхе не нужно.
- **Правило то же, что в 1С:** документ, лежащий в закрытом периоде, не
  создаётся, не правится и не удаляется. Под замком: оформление заказа этой
  датой, правка/перенос/удаление старого заказа, возврат, откат оплаты, выдача
  сдачи, оплата и общая выплата задним числом, трата, кассовая запись,
  приходная накладная и её отмена.
- **НЕ под замком:** инвентаризация и списание — они двигают только текущий
  остаток склада, а он точка во времени, не период (и в прибыль после отказа от
  остатков не входит). Если это понадобится закрыть — та же одна строчка.
- Закрывать будущее нельзя: в нём ещё ничего не произошло. Открыть обратно
  можно — это защита от случайной правки, а не бетон; и закрытие, и открытие
  пишутся в журнал действий.
- Одна дата, а не запись на каждый месяц: периоды закрывают подряд, и «закрыто
  по 31.07» — ровно та фраза, которой это называют вслух.

Тесты — `finance/tests_period.py` (14 штук: сам замок, каждая закрытая дверь,
снятие замка).

**Касса и банк (2026-08-14).** `finance.CashEntry` — кассовая книга; экран
«Касса» (`pages/admin/Cash.jsx`, за финансовым паролем). Раздела не было вовсе:
система знала обороты (выручка, расходы, долги), но не остаток, а «сколько
сейчас в ящике» — это то, чем закрывают день.

- **Два счёта:** `CASH` и `BANK`. Наличные идут в ящик, MBank/DemirBank/онлайн —
  на счёт: складывать их значит получить остаток, которого при пересчёте не
  окажется.
- **В кассу попадает ПРИНЕСЁННОЕ, а не зачтённое.** Заказ на 36, клиент дал
  100 — приход 100, потому что в ящике лежит 100; 64 уйдут расходом при выдаче
  сдачи (`give_change`). Записывай мы зачтённые 36, выдача сдачи увела бы кассу
  в минус на ровном месте. Откат оплаты списывает зачтённое ПЛЮС невыданную
  сдачу — она физически в ящике.
- **Система пишет сама** (`finance/cash.py`, вызовы из `sales/sale_service.py` и
  `unpay`): оплата при оформлении, погашение долга, выдача сдачи, возврат, откат
  оплаты. Датируется ДАТОЙ СОБЫТИЯ (заказа/платежа), а не моментом ввода.
  Такие записи (`is_auto`) не правятся и не удаляются: они отражают чеки, и
  правка развела бы кассу с продажами.
- **Руками вносят то, чего система знать не может:** закуп за наличные,
  зарплату, инкассацию, внесение денег. Статьи оплат/сдачи/возврата руками
  запрещены сериализатором.
- **Пересчёт** (`POST /finance/cash/count/`) — как инвентаризация склада: пишет
  разницу отдельной строкой, а не переписывает историю. Недостача остаётся
  видна: затереть её значит потерять единственный след пропажи.
- **Остаток всегда «на сейчас», обороты — за период** (`/finance/cash/balance/`).
  «Остаток за июль» у двух людей означал бы разное.
- Открывающий остаток вводится вручную статьёй «Внесение денег»: истории
  движений до включения кассы у системы нет, и выдумывать её нельзя.

Тесты — `finance/tests_cash.py` (22 штуки).

**Печатные формы (2026-08-14).** Их не было ни одной, и юрлицу нечего было
отдать: без счёта оно не заплатит, без накладной не примет товар. Теперь по
заказу печатаются **товарный чек, накладная и счёт на оплату**
(`components/PrintDocs.jsx`, кнопка «Печать» в «Чеках» — и у админа, и у

(`components/PrintAct.jsx`, кнопка в карточке).

- Печатает **браузер** (`window.print`), серверной генерации PDF нет. То же окно
  печати умеет «Сохранить как PDF», а вторая вёрстка тех же таблиц на сервере
  стоила бы дороже, чем всё остальное вместе. Предпросмотр свёрстан листом А4:
  что видно на экране, то и уйдёт на бумагу. `@media print` в `index.css`
  прячет `.shell`, `.no-print` и тосты, оставляя только `.print-sheet`.
- Шапка и подписи — из **реквизитов организации** (`finance.CompanyProfile`,
  singleton; Финансы → «Реквизиты для документов»). Эндпоинт `/finance/company/`
  отдельный от `/finance/settings/` ИЗ-ЗА ПРАВ: читать реквизиты должен любой
  сотрудник (иначе складовщик напечатает накладную без шапки), а настройки
  финотчёта ему закрыты. Менять — только админ.
- **Счёт не даётся, пока не заполнены банк и расчётный счёт** (`has_bank` в
  ответе): платить по такому счёту некуда. Вкладка видна, но неактивна и
  объясняет почему.
- **Сумма прописью** — `frontend/src/utils/amountInWords.js` («Четыре тысячи
  девятьсот пятьдесят четыре сома 00 тыйын»). В счёте и накладной она
  обязательна: по ней сверяют цифру.
- Колонка «Ед.» берётся из `TransactionItem.unit_label` (добавлено в API): у
  резки — пог.м, у целого листа — шт, у куска — кв.м. На фронте вывести её было
  не из чего.
- **Акт сверки** считает «оплачено» по заказу как `amount_paid` минус поздние
  записи `sales.Payment`. Оплата, принятая ПРЯМО В КАССЕ, записи `Payment` не
  создаёт — та заводится только при погашении долга; без этой поправки акт
  показывал бы все заказы неоплаченными. Сальдо акта обязано совпадать с долгом
  клиента, это проверяет `sales/tests_print_data.py`.
- **ИНН покупателя** (`Client.inn`, только у ОсОО) — без него бухгалтерия юрлица
  счёт не проведёт. Спрашивается только у юрлица, правится в карточке клиента.

Тесты: `finance/tests_company.py` (права на реквизиты), `sales/tests_print_data.py`
(единицы измерения и сходимость акта).

**Способы оплаты** (`Receipt.PaymentMethod`): `CASH`, `MBANK`, `DEMIRBANK`,
`ONLINE`. Наличные/MBank/DemirBank — товар отдаём сразу, поэтому склад
списывается независимо от оплаты. **Сколько приняли — указывает кассир явно;
сумма НЕ указана значит не платили, и весь заказ уходит в долг.** Раньше
пустое поле молча означало «оплачено полностью», и продажа в долг выглядела
закрытой. В кассе рядом с полем есть кнопка «Вся сумма» для обычного случая;
переплата не записывается (долг не бывает отрицательным) — лишнее показывается
как сдача. Онлайн → `PENDING` + платёжная ссылка + **QR-код**
(`payment_qr`, data-URI); списание — только после подтверждения (вебхук).

**Долг** (`Receipt.debt` property = `total_price − amount_paid − refunded_amount`,
только для незакрытых чеков): гасится через `POST .../pay/` (по умолчанию —
весь долг, либо указанная сумма, не больше остатка); ошибочно принятая оплата
откатывается через `POST .../unpay/` (возвращает чек в `PENDING`, склад не
трогает — товар уже отгружен). Список чеков сортируется должниками наверх
(`_debt`-аннотация), с кликабельной сортировкой по колонкам на фронте.

**Долг вместе с новым заказом** (`pay_debt` в checkout, только админ): гасится
ТЕМИ ЖЕ деньгами, что принесли за заказ — `amount_paid` это всё, что клиент
отдал: сначала заказ, остаток в долги от старых к новым (`_settle_old_debts` в
`create_sale`), что не пригодилось — сдача на новом чеке; `pay_full` — заказ и
долги целиком; пустая сумма без `pay_full` при долге — 400. Раньше сумма сверх
заказа становилась сдачей, а долги закрывались отдельно — вписанные «заказ +
долг» удваивались (2026-08-18, аудит п. 3; `sales/tests_pay_debt_amount.py`).

**Статусы:** `payment_status` (PENDING/PAID/REFUNDED/PARTIALLY_REFUNDED),
`fulfillment_status` (PROCESSING → READY → ISSUED, экшены `mark-ready`/
`mark-issued`, шлёт клиенту Telegram-уведомление).

**Возврат** (`refund`) — весь чек или отдельные позиции (`item_ids`).
Возвращает материалы на склад (только если чек реально был оплачен/списан со
склада — неоплаченный online-заказ восстанавливать нечего), обновляет
`refunded_amount`/статусы. Рулонные материалы восстанавливаются через
`restore_area` (FIFO, тот же порядок, в каком списывались).

**Дозаказ** (`add-items`) — добавить позиции в открытый чек позже (например,
установку или доп. материал): пересчёт итога. Склад: новые строки уходят
тогда же, когда ушли остальные строки чека (`_stock_was_deducted`): наличный
заказ — сразу, оплачен он или в долг; онлайн-счёт без подтверждения — при
`confirm_payment`. Деньги: доплата — долг: чек, бывший «Оплачено», снова
PENDING, `debt` = разница, доплату принимают через `pay` (админ), и она
доходит до кассы. Закрытый/возвращённый/выданный чек → 400 (`OrderClosed`).
UI: кнопка «+ Дозаказать» в карточке чека. По чеку с частичным возвратом
дозаказ и правка состава считают от денег НА РУКАХ (`_money_held`), а
`recalculate_total()` складывает и возвращённые строки (`sold_total`) —
см. `sales/tests_add_items_stock_debt.py`.

**Округление:** каждая строка чека (`TransactionItem.line_total`) округляется
**вверх до целого сома** (`ROUND_CEILING`); итог чека — сумма таких целых
строк. Фронт дублирует то же округление (`ceilSom`) для живого превью цены до
сохранения.

**Наименование заказа:** `Receipt.title` — необязательное название («Вывеска
для кафе»), вводится в кассе с подсказками из ранее использованных
(`GET /api/sales/receipts/titles/`), показывается под номером в списке чеков и
участвует в поиске.

**Права на цену при продаже:** `material_price` / `cut_rate` в checkout и
add-items принимаются только от админа (иначе 403; аудит п. 14). Закупочные
цифры (`Roll.purchase_cost/cost_per_sqm/cost_per_pm`,
`Material.purchase_price/stock_value`) складовщику приходят `null` — как
`cost_total`/`margin` в чеках.

**Себестоимость строки:** `TransactionItem.cost_total` — закупочная стоимость
списанного материала, зафиксированная В МОМЕНТ продажи (для рулонных — по FIFO
партиям). Снимок, как и цена: переоценка склада задним числом прибыль прошлых
заказов не двигает.

**Права:** приём оплаты долга (`pay`) и откат оплаты (`unpay`) — **только
админ**; складовщик оформляет продажи и возвраты, но деньгами не распоряжается.

**Человеческий номер заказа:** `Receipt.order_number` — сквозной инкремент
(Max+1 при сохранении), UUID `id` остаётся только внутренним ключом. Во всех
клиентских уведомлениях и чеках показывается `order_number`.

> ⚠️ Важный фикс: `Receipt.recalculate_total` использует `.filter(is_returned=False)`
> (не `.all()`), т.к. вьюха грузит чек с `prefetch_related`, и кэш устаревал
> после дозаказа. Ответы мутирующих экшенов перезагружают чек через
> `_fresh_response`.

Эндпоинты: `/api/sales/receipts/` (+ `checkout`, `refund`, `pay`, `unpay`,
`add-items`, `mark-ready`, `mark-issued`, `stats`).

## 6. Клиенты (CRM), портал клиента, рефералы

`Client`: тип PHYSICAL/OSOO, ФИО/компания, телефон (unique), telegram_chat_id,
`portal_password` (хеш, никогда не хранится и не логируется в открытом виде),
`referred_by` (FK self, related_name=`referrals`).

- **Портал клиента** (`clients/customer.py`): вход по телефону + паролем,
  который **выдаёт админ** (`POST /clients/<id>/set-password/`, `IsAdmin`).
  Пароль генерируется (6 цифр) или задаётся вручную, показывается ОДИН раз —
  в базе только хеш; «забыл пароль» решается выдачей нового. Складовщик выдать
  пароль не может (403) и видит только статус «Задан / Не задан».
  **Клиент себе пароль не заводит** — иначе кабинет с историей заказов и
  долгами доставался бы тому, кто первым вошёл по чужому номеру. Без выданного
  пароля вход отвечает `status=no_password` («обратитесь к администратору»).
  Отдельный JWT-scope (`scope=customer`, токен через `mint_customer_token`) —
  токены клиента и персонала не пересекаются (чужой scope → 401).
  `GET /api/customer/orders/` отдаёт только заказы этого клиента.
  > Одноразовый код входа существовал недолго и **удалён** вместе с полями
  > `login_code*` (миграция `clients/0006`) — остался только пароль.
- **Рефералы «кто кого привёл»:** `referred_by` фиксируется **один раз**.
  Складовщик не может изменить/снять его напрямую — только подать заявку
  (`ReferralChangeRequest`, статусы PENDING/APPROVED/REJECTED), которую
  администратор одобряет или отклоняет (страница «Заявки на рефералов»).
  Администратор может менять реферера напрямую, минуя очередь. UI показывает
  🔒, если реферер уже задан.
- **Бонус за рефералов** — фиксированная сумма (`FinanceSettings.referral_bonus`,
  редактируется в Финансах) за каждого приведённого клиента. Считается и
  показывается в карточке клиента (`ClientDetailSerializer.get_referrals`:
  count/total_value/bonus/list с LTV каждого реферала) — **в расходы
  автоматически не списывается**, это справочная цифра для решения о выплате
  вручную.
- Доступ: страница «Клиенты» есть и у **админа**, и у **складовщика**.
  Клиента можно завести заранее, не дожидаясь продажи (кнопка «+ Новый клиент»).
- **Список клиентов**: колонки «Заказов» и «Долг» с сортировкой по клику
  (`?ordering=orders_count|debt|sort_name`), фильтр периода
  (`?date_from=&date_to=` — оставляет тех, кто заказывал в эти дни; «Заказов»
  тогда считается за период), «только должники» (`?has_debt=1`) и «заказов от N»
  (`?min_orders=`). **Долг всегда «на сейчас»** и периодом не режется — клиент
  должен независимо от того, за какой месяц смотрим.
  > Заказы и долг считаются через `distinct`/подзапрос: наивный join задваивал
  > бы их на чеке из нескольких позиций (есть тесты).
- Карточка клиента показывает историю заказов (при периоде — только его заказы),
  первые 5 сразу и остальные по кнопке, чтобы при десятках заказов не
  превращаться в ленту; рядом с номером виден заголовок заказа.
- Поиск клиентов (`?search=`) — по имени/компании/телефону **и номеру чека**,
  регистронезависимо; фильтрация в Python, а не через DRF `SearchFilter`,
  потому что SQLite не умеет регистронезависимый `LIKE` для кириллицы.

## 7. Финансы (`finance` app)

Раздел «Финансы» — одна страница (`Finance.jsx`): **сверху один выбор месяца на
весь раздел** (по умолчанию текущий, кнопка «Весь период»), затем сводка, график
по дням, три блока отчёта, а ниже — списки трат «Постоянные расходы»,
«Зарплаты», «Покупки» (`ExpenseListSection`, вся история за период одним
взглядом). **Каждая строка блока кликабельна и открывает диалог своего вида
расхода** (`ExpenseKindModal`), где траты вносятся, правятся и удаляются.

> Списки внизу одно время были убраны как дубль диалогов — вернули: диалог
> показывает один вид, а месяц целиком видно только списком.

> Раньше отчёт считался **за всё время**, а списки трат фильтровались своим
> месяцем — цифры сверху и снизу жили в разных периодах. Теперь период один.

**Структура отчёта повторяет Excel заказчика — три блока с подытогами:**

| Блок | Строки | Подытог |
|---|---|---|
| **Материалы** | закуп материала, транспортные расходы, долг материала + свои виды | Σ(строки с «входит в прибыль») |
| **Постоянные расходы** | аренда, коммуналка, интернет, зарплаты, прочие + свои виды | сумма строк с «входит в прибыль» |
| **Переменные расходы** | расходники фрезы, прочие, покупка оборудования, улучшение цеха + свои виды | то же |

**Все три блока устроены одинаково:** строка = вид расхода, клик открывает
список трат за период, внизу «+ вид расхода». Закуп, транспорт и долг материала
были полями настроек (одно число на весь отчёт, без дат и расшифровки) —
миграция `0007` превратила их в виды расхода с записями.

> **Принцип: руками вводится только то, чего система знать не может.**
> Заказчик пришёл из Excel, где он вбивал всё; здесь система считает за него, а
> ручной ввод остаётся как право поправить. Считается само:
> - **Закуп материала** — по приходам на склад: каждое поступление уже несёт
>   себестоимость (`InventoryLog.actual_price × quantity`). Ручные записи по
>   этому же виду ДОБАВЛЯЮТСЯ к авто-сумме — для покупок мимо склада. В ответе
>   строки есть `auto_amount` и `manual_amount`, интерфейс показывает обе части.
>
> Руками остаются транспорт, долг материала и обычные траты (аренда, зарплаты,
> фреза) — их система знать не может.

> **Остатков материала в блоке БОЛЬШЕ НЕТ (2026-08-14, просьба заказчика).**
> Было: `начало + закуп + транспорт − конец`, где начало бралось из складского
> листа, а конец — со склада. Стало: расход материала = то, что за месяц
> потратили. Заодно ушли `FinanceSettings.stock_start` из отчёта (поле в модели
> осталось, но не используется), признак `materials.needs_setup` и защита от
> отрицательного итога — уходить в минус формуле теперь нечем. Обе колонки
> остатка убраны и из складского листа. **Прибыль от этой правки изменилась** —
> так и задумано, обратно без просьбы не возвращать.

```
прибыль = выручка − (итог Материалов + итог Постоянных + итог Переменных)

итог Материалов (с 2026-08-24) = себестоимость проданного (FIFO, авто)
                               + транспорт + свои строки блока
закуп       — НЕ расход, а оборот: карточка «Склад (оборот)» в отчёте
              (закуп за период + стоимость склада сейчас)
инвестиции  — отдельный блок; ни в прибыли, ни в плитке «Расходы»
```

**Виды расхода — справочник, а не перечисление в коде.** Админ добавляет свои
строки («Реклама», «Налоги», «Ремонт станка») кнопкой «+ вид расхода» в любом из
четырёх блоков (включая «Инвестиции» — там галки нет, флаг всегда снят):
название, блок и галка «уменьшает прибыль». Встроенные виды
переименовать можно, удалить — нет; блок у встроенного не меняется (на коды
`TRANSPORT` / `SALARY` / `MATERIAL_PURCHASE` / `MATERIAL_DEBT` опирается порядок
строк отчёта). Вид с записями не удаляется, а **скрывается** (`is_archived`), как
товар на складе.

Ключевые правила (все — решения заказчика):
- **Долг материала — справочно, в итог НЕ входит:** материал, взятый в долг,
  уже посчитан в строке «закуп», иначе задвоился бы. Технически это обычная
  строка со снятым флагом `in_profit` — тот же механизм, что у оборудования.
- **Транспорт — вид расхода блока «Материалы»**, в его формуле участвует. Из
  переменных расходов он убран — иначе считался бы дважды.
- **Оборудование и улучшение цеха** (и любой свой вид со снятой галкой) видны в
  блоке, но в подытог и в прибыль не входят: это инвестиции, станок за 300 000
  не должен делать месяц убыточным.
- **Выручка — по ВСЕМ заказам периода** (кроме отменённых), по дате заказа,
  минус возвраты. Заказ, отданный в долг, — тоже выручка: материал списан,
  работа сделана. Раньше считались только полностью оплаченные чеки плюс
  предоплаты по открытым, и месяц, отработанный в долг, выглядел пустым. Рядом
  с суммой показано, сколько из неё уже на руках (`revenue_paid`) и сколько ещё
  должны (`client_debt`). Та же формула — в графике по дням и в «Обзоре»:
  раньше три экрана считали выручку тремя разными способами.

**Себестоимость проданного (COGS)** — `TransactionItem.cost_total`, суммируется
за период и показывается блоком «Себестоимость и маржа». Считается точно (FIFO
по партиям, снимок в момент продажи), но **в прибыль не идёт** — прибыль считает
блок «Материалы». Оставлена как справочная цифра для сверки маржи.

**Модели:**
- **`ExpenseKind`** — вид расхода: `code`, `name`, `block`
  (MATERIALS/FIXED/VARIABLE), `in_profit`, `is_builtin`, `position`,
  `is_archived`. Встроенные создаёт миграция `0006`.
- **`ExpenseEntry`** — одна трата: вид, «за что / кому», сумма, дата,
  примечание. Одна таблица на все три блока. У зарплат в `name` пишется имя
  сотрудника — мастера и резчики не заводятся как пользователи.
  > Расходы **вносятся записями с датами**, поэтому их нужно заполнять каждый
  > месяц — иначе следующий месяц покажет ноль.
- **`FinanceSettings`** — остались только `stock_start` (остаток материалов на
  начало) и `referral_bonus`. Закуп, транспорт и долг материала переехали в
  виды расхода (миграция `0007`).

> Миграция `finance/0006_expense_kinds` перенесла данные из старых
> `Expense`/`FixedExpense`/`SalaryPayment` во встроенные виды один-в-один и
> удалила старые таблицы. Обратный ход написан.

**Эндпоинты:**
- `/api/finance/report/?date_from=&date_to=` — P&L: три блока строками
  (`{id, code, name, in_profit, amount}`), выручка, долг клиентов, COGS, маржа.
- `/api/finance/expense-kinds/` — справочник видов (+ `?archived=1`, action
  `restore`). `/api/finance/expense-entries/` — траты (`?kind=`, `?year=&month=`,
  `?date_from=&date_to=`); **без пагинации**, иначе месяц молча обрезался бы.
- `/api/finance/daily/?year=&month=` — посуточный P&L (`DailyProfitChart`):
  постоянные расходы месяца размазаны поровну по дням, себестоимость падает на
  день заказа; будущие дни без прибыли/убытка.
- `/api/finance/material-report/` — данные и для складского листа заказчика, и
  для таблицы «Резка и продажи». Фильтр `?year=&month=` или `?date_from=&date_to=`.
  > **Складские колонки считаются формулой листа заказчика:**
  > `остаток на начало + поступление − проданные = остаток на конец`.
  > **Остаток на начало система переносит с конца прошлого месяца сама**
  > (`finance/material_sheet.py`): вписать его нужно ОДИН раз — в месяце, с
  > которого начинают вести учёт, — а дальше цепочка идёт вперёд. Вписанное
  > вручную значение (`MaterialMonthOpening`) всегда побеждает расчёт и
  > помечается в интерфейсе уголком; так правится инвентаризация или закупка
  > мимо склада. Ручных значений нет вообще — считаем с нуля от первого
  > движения. `opening_month` в ответе равен null, если период не совпал с
  > целым месяцем: остаток на начало привязан к месяцу, вводить некуда.
  > Материал считается **в листах**, если у него задана `piece_area`, **рулон
  > (`sells_by_metre`) — в погонных метрах** (поступление по партиям — площадь
  > ÷ ширина партии, продажи — метры METER-строк, остаток — `metres_remaining`;
  > `counted_in = "METER"`, аудит п. 11), иначе в своей единице (`counted_in`).
  > `stock` — живой остаток системы «на сейчас», к формуле он не относится.
  > Откат остатка назад по движениям склада **пробовали и отказались**: он
  > требует, чтобы каждое движение за всю историю было записано без единой дыры
  > (продажи складского лога не пишут, возврат рулонного материала тоже), а на
  > живых данных цифры разъезжаются и в таблице появляются отрицательные остатки.
- `/api/finance/unlock/` — проверка `FINANCE_PASSWORD`, гейтит `/admin/finance`
  и `/admin/dashboard` (`FinanceGate.jsx`, разблокировка держится 30 минут).

## 10. Известные открытые вопросы / технический долг

**Открыто:**
- **Бэкапы прод-базы не настроены** — готовая строка для cron есть в
  `DEPLOY.md`. Пока боевых данных нет (см. `CONTINUE_HERE.md`), это не горит,
  но должно быть сделано до того, как заказчик введёт первый настоящий заказ.
- **HSTS выключен** (`SECURE_HSTS_SECONDS=0`) — включить (`31536000`), когда
  убедились, что https стабилен.

  Excel нет, поэтому списанное «растворяется» в остатке на конец: следующий
  месяц начнётся с завышенного остатка, пока его не поправят руками.

  выдумываем. Если склад принимают без цены, «закуп материала» будет занижен,

- **SSH-доступ к серверу у ассистента отсутствует** — деплой выполняет
  пользователь вручную (см. `DEPLOY.md`). Ключ на сервер не добавлен.
